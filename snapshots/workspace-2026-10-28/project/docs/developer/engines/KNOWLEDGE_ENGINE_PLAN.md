## 책임과 기존 엔진 경계

새 기관·경제 개념을 모두 미리 구축하지 않고 실제 요청/교정/출처 변경/반복 실패를 계기로
관련 지식을 축적한다. 공유 저장소에 기록하되 조회·검증 상태/적용 범위·갱신 관리는 이 엔진이 담당한다.
기관 원문 탐색은 discovery, 메타데이터 추출은 metadata, 기관 간 개념 연결은 mapping,
실제 다운로드는 connectors/ingestion, 코드 개선은 Improvement Engine에 남긴다.
같은 정보를 여러 엔진이 각각 사실 DB로 복제하지 않는다.

| 지식 종류 | 저장·적용 원칙 |
|---|---|
| 사용자 설명/교정 | 원문·작업/기관/개념 범위 보존. 검증되지 않은 공식 사실로 취급하지 않음 |
| 공식 근거/검증 기록 | 출처·확인일·분류/자료 버전·유효 기간·미확인/충돌 포함 |
| 추론/일반화 후보 | 전제·근거·적용 조건·반례·검토 상태를 기록. 기본 사실 조회에서 제외 |

개념은 기관의 조작적 정의와 구분한다. 분류 축과 포함/제외·중첩·상호배타·미확인 관계,
포괄성/합산 가능성 여부를 별도로 기록한다. 모든 분류를 트리나 상호배타 집합으로 만들지 않는다.
CP/TIC 등에 관한 앞선 사용자 예시는 문제 유형의 설명이며 이번에 실제 정의를 검증한 것이 아니다.

## 두 실행 경로

**요청 처리 경로:** 관련 지식 제한 조회 → 필요한 근거만 읽기 → 후보/질문/결과에 활용.
이번의 명시적 설명/교정은 짧게 기록하되 전체 지식의 재검증·추론까지 함께 실행하지 않는다.
필수 의미의 충돌/만료는 해당 부분만 조사하거나 NEEDS_REVIEW와 제한을 보고한다.
사용자 의도는 질문으로 좁힐 수 있지만 기관 원통계의 모호함은 사용자 선택으로 사라지지 않는다.

**지식 갱신 경로:** 새 근거 추출·검증 후보·인접 개념 추론·색인 재구축을 별도 작업으로 처리.
필수가 아닌 확장은 결과 제공을 기다리게 하지 않는다. 작업은 별도의 예산·상태·체크포인트로
명시적으로 실행하며, 지금 자동 실행기나 예약 작업이 있다고 가정하지 않는다.
실행 중인 요청은 고정된 지식 버전/참조를 사용하고, 갱신 결과로 이미 확정된 의미를 조용히 바꾸지 않는다.

## 자료가 쌓여도 매번 전부 읽지 않기

1. 기관/데이터셋/개념/분류 축·버전·검증 상태·유효 시점을 구조화해 색인한다.
2. 전체 이력과 분리된 조회용 현재 기록을 유지한다. 원문/이력은 참조로 연결하고 필요할 때만 읽는다.
3. 특정 기관·자료 → 관련 개념 → 다른 기관의 관련 근거 순으로 범위를 제한 확장한다.
   기관 미지정도 주제/지역/기간으로 시작하며 전체 문서를 무차별 검색하지 않는다.
4. 반환 수·읽을 행/근거 바이트·관계 탐색 깊이·시간·동시 작업·캐시 메모리 상한을 둔다.
   큰 결과는 페이지/청크로 처리하고 전부 메모리나 프롬프트에 올리지 않는다.
5. 캐시는 요청 범위/분류·근거 버전/검증 상태/시점을 구분하고 교정·취소·대체·만료 시 무효화한다.
6. 조회한 범위·중단 사유·미확인 여부를 반환한다. 한도를 다 썼다고 근거가 없다고 결론내리지 않는다.

동일 범위의 반증·상충 기록은 별도로 연결/색인해 기본 후보와 함께 확인한다. 상위 몇 건만
남겨 중요한 반증을 놓치면 빠른 검색이어도 실패다. 충돌 전체가 예산을 넘으면 충돌 존재와
미검토 범위를 보고한다. 과거 시점 요청은 현재 요약으로 대체하지 않는다.

초기는 SQLite의 구조화된 조회와 실제 쿼리 계획을 점검한다. 필요성이 측정된 경우에만
추가 검색 도구를 검토한다. 별도 벡터 DB, 매 요청 임베딩 전체 재생성, 대형 관계 그래프의
전수 순회는 기본 전제가 아니다. 용량 확보를 위해 원본을 자동 삭제하지 않는다.

현재 HistoryStore는 작업 JSON 안에 시도 이력을 저장한다. 이를 그대로 기관/개념 검색의
매 요청 전체 로딩 대상으로 쓰지 않는다. 11~12회차는 기존 작업 이력·JSON/hash와
SQLite `user_version=2`를 유지하면서 별도 조회용 색인/투영을 구현했다.

### 11회차 반영 상태

`AuditStore`는 피드백 원문 및 append-only 수정/검토/취소 이벤트를 저장한다.
`KnowledgeStore`는 사용자 주장·공식 근거·추론과 기관/데이터셋/개념/축·버전·유효 범위·근거·
대체/취소 관계를 추가 기록한다. 전 기관 재계산은 수행하지 않는다. 전체 구현 범위와 573개
로컬 테스트 결과는 `docs/developer/history/ITERATION_11_REPORT.md`에 있다.

### 12회차 Gate D 구현 상태

`knowledge_current`는 append-only 원문/이벤트와 분리된 가변 조회 투영이다. 신규 입력·검토·취소는
해당 레코드만 투영하고 세대를 올린다. `refresh_index`는 batch 1~1,000의 명시적 페이지 작업이며
진행 중인 재색인에서는 완전성 표시와 재사용을 보류한다. 쿼리는 결과 1~1,000행, 근거 byte
1~1,048,576, 제한 시간 1~5,000ms 범위로 제한한다. 기본값은 각각 100행, 262,144 bytes,
250ms다. 캐시는 요청 범위·시점·source version·정정 override·검색 정책 fingerprint·색인 세대에
묶고 TTL 1초, 128개/1 MiB 상한을 적용하며 상태 변경은 캐시를 무효화한다. 외부 store 인스턴스의
갱신도 세대가 달라지면 stale cache hit가 되지 않는다.

개념 확장은 versioned `ConceptSearchPolicy`의 근거 있는 `subtype`만 최대 깊이 4, 후보 개념 ID
최대 16개로 탐색한다. `related`는 추가하지 않으며 자식 concept 질의는 형제까지 넓히지 않는다.
확장 결과에는 경로/근거/깊이를 표시하고 항상 비재사용 후보로 반환한다. GDP 상위 질의가 명목·실질
개념을 찾더라도 통계적 등가성이나 자동 대체가 아니며 사용자가 의미를 선택해야 한다.

예산 초과·미완료 갱신에서는 partial/uncertainty를 반환하고 전부 재사용하지 않는다. 제한으로
충돌 후보를 모두 검사할 수 없으면 `potential_conflicts_unchecked_due_to_row_budget`도 표시한다.
공식 근거는 요청한 각 기관/데이터셋/개념/분류 축과 저장 범위가 맞아야 재사용 가능하다.
범위가 더 넓은 사실은 후보로만 보여준다. 사용자 지시는 같은 기관의 확인 필요 제안만 가능하며,
추론은 검토 승인이나 공식 사실 승격이 차단된다.

## 성능 및 정확성 검수

08회차의 제한된 검색 관계 정책은 docs/developer/planning/CONCEPT_SEARCH_REVISION_PLAN.md를 따른다.
GDP 개념군의 명목·실질 포함 같은 제품 검색 규칙을 기관의 공식 등가성 사실로 저장하거나
승격하지 않는다. 향후 지식 엔진은 검색 관련성, 출처 정의·매핑, 통계적 대체 가능성을
별도 상태와 근거로 관리하고 검색 정책 버전이 바뀌면 이전 확인의 재사용을 제한해야 한다.

기준 환경·자료 크기/구성 및 예산 측정 결과는 `docs/developer/history/ITERATION_12_REPORT.md`와
`reports/iteration_12_benchmark.json`에 기록한다. 아래 수치는 synthetic fixture와 단일 Windows
호스트 측정이며 제품 운영 SLA나 모든 디스크/동시 부하의 성능 보증은 아니다.

- 저장 지식 재사용, 처음 보는 개념, 상충 분류, 기관 미지정, 만료/교정 직후 조회를 회귀 테스트한다.
- 100/1,000/10,000개 합성 기록에서 앱 캐시를 비운 조회 및 warm cache의 p50/p95, Python allocation peak를 측정했다. 별도 store 인스턴스의 세대 기반 캐시 무효화와 read snapshot 도중 writer가 시작하는 deterministic interleaving을 테스트했으며, 지속 동시 reader/writer 처리량·stress는 측정하지 않았다.
- 읽은 행/바이트·확장 단계·캐시 크기·갱신 대기와 잘못된 범위 적용/충돌 발견 여부를 기록한다.
- 결정적 테스트로 예산 소진의 안전 중단·미확인 보고, 무한 관계 순회 방지, 캐시 무효화,
  추론/미검증 기록의 사실 승격 방지, 시점/기관 범위 격리와 증거 참조 보존을 검증한다.
- 특정 실행 환경에 민감한 시간 측정은 별도 benchmark로 보고하고, 단위 테스트에는 모의 시계와
  처리량 카운터를 사용한다. 빠른 응답과 의미 정확성/반증 보존을 모두 만족해야 한다.

## 회차 배치와 남은 결정

- 11: 범위·버전·근거가 있는 사용자 설명/교정과 지식 입력.
- 12: **완료** — 제한 조회·색인·현재 기록·캐시·갱신 분리 및 Gate D 성능/정확성 검수. 제품 CLI/채팅 연동은 구현 범위 밖.
- 13: 격리된 추론/일반화 후보와 검토·개선안. 사실·코드 자동 승격 없음.

예산 수치·최종 스키마/현재 기록 갱신 방식·별도 갱신 실행기는 해당 회차의 측정과 검토로 확정한다.
매 사용자 요청마다 기술 예산을 다시 물을 필요 없이 검증된 기본 설정을 재사용한다.
부족한 자원 때문에 의미 확인이 생략되면 안 되며, 추가 조사가 필요하면 비용과 범위를 설명한다.

11~12회차는 로컬 SQLite/fixture 기준이다. 공식 기관 페이지·실제 API·원문 근거는 확인하지 않았다.
전체 pytest는 578 passed, Ruff/diff check 통과다. synthetic 100/1,000/10,000건에서
앱 캐시 미사용 p95는 8.516/16.625/13.793ms, warm p95는 4.309/8.175/5.944ms,
Python allocation peak는 49,536/71,022/127,673 bytes였다. SQLite native memory/RSS 및
동시 writer 부하 전체는 측정 대상이 아니다. 실제 수치와 해석은 12회차 보고서 참조.
