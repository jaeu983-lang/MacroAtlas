# MacroAtlas 운영 계획

**기준일:** 2026-10-25
**이 문서의 역할:** 반복 운영의 주기, 두 작업 트랙의 관계, 기관별 시험 기준, 책임자를 정의합니다. 제품 범위는 [PROJECT_PLAN.md](../../PROJECT_PLAN.md), 근거 보고서는 [ITERATION_20_REPORT.md](../developer/history/ITERATION_20_REPORT.md)와 기준선/변경 로그를 따릅니다.
**절차별 runbook:** API 설정, live canary와 장애 대응은 [OPERATOR_RUNBOOK.md](OPERATOR_RUNBOOK.md)를 보세요.

## 한 문장으로 운영 방식

**공통 엔진은 한 벌로 유지하고, 오류·피드백 개선은 매주, 메모리·성능 검토는 2주마다, 기관 연결은 필요할 때 각각 진행합니다.** 서로 독립된 작업은 offline 단계에서 나란히 할 수 있습니다. 실제 기관 호출은 공통 엔진과 해당 기관의 준비를 모두 확인한 뒤 그 기관만 따로 시작합니다.

## 현재 기준선

- 조사 대상은 21개 기관·서비스입니다.
- 공식 API 문서 확인: 15개. 조사 범위에서 문서 명세 미확인: 6개. API 미제공을 공식 문서로 확인한 곳: 0개.
- 미확인 6개는 “API가 없다”가 아니라 추가 문서 조사가 필요하다는 뜻입니다.
- World Bank USA/WDI/GDP 고정 workflow는 과거 제한 live 검증이 있습니다. Iteration 30에서는 FRED GDP와 BoE Bank Rate bounded request가 live contract/hash 확인됐고, TIC MFH·Table 3D는 live 원본 저장/hash read-back 뒤 현재 validator를 offline 재실행해 통과했습니다. TIC 두 원래 receipt는 실행 당시 `live_needs_review`였으므로 Gate U를 통과한 것은 아닙니다.
- Iteration 30의 7개 live canary는 원 실행 기준 2/7 통과, 최신 저장 응답 contract 근거 4/7이며 Gate U는 미통과입니다. Census는 `LICENSE_SECURITY/NEEDS_REVIEW`, BLS 두 경로는 `TRANSIENT/FAILED_RETRYABLE`이었고 당시 구체 원인은 보고되지 않았습니다. 예산 소진 후 재시도하지 않았습니다. 상세는 [canary 보고서](../developer/testing/LIVE_CANARY_REPORT.md)를 따릅니다.
- BEA와 e-Stat은 제한된 API 클라이언트와 mock fixture가 있으나, dataset collector 연결과 live 인증·수집은 미검증입니다.
- 자연어 지시를 받는 제품 에이전트 UI는 아직 구현되지 않았습니다. 저장소에는 Python 서비스와 데이터 엔진이 있습니다.
- 현재 개선 분석기는 오류·피드백을 읽어 사람 검토용 후보를 만들며, 코드를 자동 수정하지 않습니다.

기관별 문서·인증·API 상태의 원본 근거는 [기관 카탈로그](reference/INSTITUTION_CATALOG.md), [API 조사표](reference/INSTITUTION_API_AUDIT.md), 실행 프로필을 함께 확인합니다.

## 두 트랙은 나란히 운영합니다

| 구분 | Track M — 유지보수 | Track C — 기관 연결·업데이트 |
|---|---|---|
| 목적 | 지금 있는 공통 엔진의 정확성, 복구성, 보안, 자원 사용을 개선 | 기관별 공식 API를 조사하고 실제 사용 가능한 커넥터를 추가 |
| 시작 시점 | 주간 피드백 점검, 격주 메모리/성능 점검 | 새 통계 수요가 생기거나 기존 커버리지가 부족할 때 |
| 변경 위치 | orchestration, 공통 계약, ingestion, storage, retry, 기록·계측 | 기관별 connector, 기관 문서, source fixture |
| 먼저 확인할 것 | 재현 가능한 오류와 같은 조건에서의 성능 근거 | 공식 문서, 실제 dataset 식별자, 인증, 언어·쿼터·개정 조건 |
| 완료 기준 | 회귀 없이 같은 입력에서 개선이 반복 재현됨 | 공식 문서와 기관 fixture를 통과하고 저장·재조회·복구됨 |
| 실 API 진입 | 공통 platform gate를 통과해야 함 | 해당 기관 source gate도 별도로 통과해야 함 |

M과 C는 조사·설계·fixture 등 독립적인 offline 작업을 동시에 할 수 있습니다. 공통 입출력 계약이 바뀌면 관련된 모든 connector fixture를 다시 확인합니다. Track M의 최적화 완료를 기다려야 Track C를 시작하는 것도 아니고, 기관별 구현 완료를 기다려야 유지보수를 시작하는 것도 아닙니다.

### 흐름과 합류 지점

Track M과 Track C의 경계 및 사용자에게 심각한 오류를 알리는 원칙은 [개발자 아키텍처](../developer/ARCHITECTURE.md)에 요약했습니다. Track M은 기존 엔진·모듈의 오류·피드백과 성능 근거를 다루고, Track C는 새 기관 connector를 준비합니다. 독립된 offline 작업은 병행할 수 있으며, 실제 live 요청에서만 공통 platform gate와 기관 source gate가 합쳐집니다. 이 구분은 운영 방식의 계획이지 현재 예약 자동화, 멀티에이전트 동시 실행 또는 자율 코드 수정 기능이 있다는 뜻은 아닙니다.

## 반복 주기와 예상 작업량

기간은 한 명의 개발자 기준 계획치입니다. 실제 데이터셋의 인증·문서 상태·응답 구조에 따라 달라지며, 주기 안에 완료하려고 검증 단계를 생략하지 않습니다.

| 주기 | 할 일 | 계획 시간 | 완료할 때 남길 것 |
|---|---|---:|---|
| 매주 | 오류와 사람이 남긴 피드백 분류, 재현, 한두 개 우선 수정, 회귀 확인 | triage 60–90분; 수정은 보통 0.5–2 작업일 | 재현 절차, 범위, 수정 diff, fixture, 검사 결과, 남은 한계 |
| 2주마다 | 대표 workload에서 메모리·CPU·지연을 측정하고 병목을 확인; 근거가 있으면 작은 최적화 | 측정·검토 2–4시간; 수정은 보통 0.5–2 작업일 | 같은 조건의 before/after, 정확성 invariant, 원시 결과 |
| 필요할 때 | 기관 API 확인, source 문서 작성, adapter/fixture, 통합 | 명세가 분명한 단순 API는 1–3 작업일; SDMX·인증·대용량·개정 처리가 복잡하면 3–7일 이상 | 기관별 문서·fixture·수집/복구 결과와 live 준비 상태 |
| 별도 승인 후 | 준비된 기관의 외부 호출 시험 | 15–30분 canary → 2시간 → 6시간 이상 | 기관별 요청량·성공률·오류·원본 hash·중단/복구 결과 |

API 미확인 기관은 공식 자료 조사에 처음 0.5–2일을 계획하되, 공개 명세를 찾지 못하면 조사/파일 경로 검토 작업으로 남깁니다. 정해진 날짜에 API를 만들어낸다고 약속하지 않습니다. 작업 기간은 직렬로 합산하지 않습니다. M의 독립 측정과 C의 문서/fixture 작업은 같은 주기에 나란히 진행할 수 있습니다.

보안·데이터 손실·반복적 오수집 같은 중대 사건은 주간 회의를 기다리지 않고 즉시 중단·분류합니다.

## Track M: 주간 오류·피드백 개선

1. 사람의 지적, 실패 run, 잘못된 결과를 작업 ID·기관·dataset/series·실행 단계에 연결합니다.
2. 피드백을 사용자 의도, 공식 데이터 의미, connector 오류, 공통 엔진 오류, 사용 절차 문제로 분류합니다.
3. 저장된 raw/fixture로 재현할 수 있는 가장 작은 사례를 만듭니다. 외부 호출은 기본 재현 수단으로 쓰지 않습니다.
4. 수정은 원인이 있는 공통 모듈 또는 해당 기관 adapter에 한정합니다.
5. 정상/오류 fixture, 관련 회귀, raw·단위·결측·출처 invariant를 검사합니다.
6. 사람이 diff와 보고서를 검토한 다음에만 통합합니다. 반복된 지시만으로 기관 사실이나 공통 규칙을 자동 승격하지 않습니다.

매주의 목표는 티켓 수를 채우는 것이 아니라 재현 가능한 문제를 안전하게 닫는 것입니다. 재현이 안 되면 근거와 추가로 필요한 입력을 남기고 보류할 수 있습니다.

## Track M: 격주 메모리·성능 검토

**메모리 최적화**는 저장된 원자료 삭제나 무조건 압축을 뜻하지 않습니다. 요청당 최대 RSS, Python 할당, 처리시간과 조회량을 측정하고, 정확성과 복구를 유지하면서 반복되는 비용만 줄입니다.

1. 시나리오, 고정 fixture, seed, Python/OS, 캐시 상태, dataset 범위를 고정합니다.
2. 전체 시험과 각 단계의 wall time, CPU, peak RSS, Python allocation, API 요청 수/중복, 전송량을 따로 기록합니다.
3. 환경 변동을 파악하도록 최소 3회 예비 실행을 하고, 수치가 안정되면 이전 기준선과 후보를 같은 조건으로 각각 30회 반복합니다. 외부 API가 포함된 결과는 fixture 수치와 분리합니다.
4. 속도만 보지 않고 hash·행 수·기간·단위·결측/0 구분·저장 read-back·재개 결과를 확인합니다.
5. 측정 차이가 반복되지 않거나 실행환경 변동과 구분되지 않으면 코드를 바꾸지 않습니다. “수정 없음”도 올바른 결과입니다.
6. 최적화로 raw, provenance, 원자성, idempotency, 재시도·재개 성질이 바뀌면 해당 회귀 검사가 모두 통과해야 합니다.

초기 판단 기준은 반복 변동보다 큰 개선이 측정되고 정확성 조건이 전부 유지되는 것입니다. 첫 두 격주 주기의 실제 변동 폭을 보고 최소 유의 개선 기준을 조정합니다. 이 저장소에서 기준선의 전 기관 성능이나 기관별 live 성능을 이미 측정했다고 간주하지 않습니다. 상세 절차는 [성능 최적화 계획](../developer/performance/PERFORMANCE_OPTIMIZATION_PLAN.md), 수치 근거는 [기준선 보고서](../developer/performance/BASELINE_REPORT.md), [20회차 재측정](../developer/history/ITERATION_20_REPORT.md)을 봅니다.

## Track C: 기관 API를 하나씩 준비

기관을 추가할 때는 공통 엔진을 복제하지 않고 source-specific connector와 문서/fixture를 먼저 만듭니다.

### 우선순위 정하기

1. 사용자가 실제로 필요한 통계와 기관을 먼저 적습니다.
2. 공식 API 문서가 있고, 필요한 표/시계열과 인증 방법을 확인할 수 있는 곳을 우선합니다.
3. dataset 범위, 언어 응답, 호출 예산, 개정 정보, 이용 조건, 예상 fixture 확보 난이도를 비교합니다.
4. 기존 adapter와 같은 provider/credential을 공유하면 한 공급자의 총량으로 계획합니다.
5. 문서 미확인 기관은 조사 티켓으로 분리하고 endpoint를 추정해 호출하지 않습니다.

초기 후보로 BEA와 e-Stat을 검토할 수 있습니다. 두 기관은 limited client/mock 상태이므로 데이터셋 선정, workflow 연결, credentials 준비, live 성공은 다시 검증해야 합니다. 어느 쪽을 먼저 할지는 실제 연구 수요를 기준으로 정합니다.

### 기관 한 곳의 완료 순서

1. **공식 문서 확인:** API base/버전/방법, 표·시계열 식별자, 인증, pagination, 제한, 라이선스, 수정/vintage, 언어.
2. **기관별 계약 기록:** 문서 URL과 확인일, 요청·응답 예시, 알려진 예외, 정확한 테스트 범위를 기록합니다. 키 값은 문서에 쓰지 않습니다.
3. **mock fixture:** 정상, 빈 결과, 누락/0, 오류 코드, pagination, 필드 추가/변경, 다국어 표기를 재현합니다.
4. **adapter와 공통 연결:** HTTP와 파싱은 source connector, 단계 흐름은 기존 orchestration을 사용합니다. API client 하나를 live 수집 지원 전체로 오인하지 않습니다.
5. **오프라인 E2E:** discovery/확인 → 요청/수집 → raw·manifest 저장 → 정규화/검증 → SQLite read-back → 오류 재개를 테스트합니다.
6. **source gate:** 필요한 데이터셋과 범위에서 정확성, 출처, 단위, 주기, 결측, revision, 인증 누출 방지, 쿼터 정책을 확인합니다.
7. **live readiness review:** 운영자가 키 존재를 자기 PC에서 확인하고, 허용 도메인·네트워크·약관·호출 budget·stop 조건을 준비한 뒤에만 live gate에 올립니다.

기관마다 별도 문서와 fixture가 필요하고, 모든 기관이 공통 규칙을 별도로 복제할 필요는 없습니다. 공통 connector contract와 conformance test는 한 벌로 관리하고, source별 차이는 그 기관 자료에 둡니다.

## 무작위 표본과 장기 검증

무작위 시험은 “아무 데이터를 무제한으로 받기”가 아니라 커버리지를 체계적으로 넓히는 통제된 선택입니다.

- 기관/API 계열/응답 형식/주기/기간 크기/언어/인증/개정 처리 축을 정하고, seed를 기록해 표본을 다시 만들 수 있게 합니다.
- 각 source에서 아직 시험하지 않은 층을 우선 섞고, 같은 표의 이웃 series만 계속 고르지 않도록 dataset 단위 층화와 holdout을 둡니다.
- 매 실행에서 랜덤 표본과 필수 미검증 목록을 함께 관리해 우연히 빠진 기관이 장기간 방치되지 않게 합니다.
- fixture replay는 자주 실행합니다. live 재조회는 기관별 호출 budget에서 뽑은 소수 표본만 사용합니다.
- run마다 source, API/version, dataset/series ID, seed, request count, bytes, 결과 hash, 결측·0, 오류·복구, revision 변화, 실제 실행 여부를 기록합니다.
- raw를 덮어쓰지 않습니다. 같은 API의 새 응답이 달라지면 파서 오류인지 공식 개정인지 구분합니다.

## 기관별 실 API 진입 게이트

다음 단계로 가기 전에 현재 source의 게이트가 통과되어야 합니다.

| 단계 | 통과 기준 | 다음으로 넘어가는 조건 |
|---|---|---|
| 0. 문서·데이터셋 | 공식 API 문서와 대상 표/series, 이용 조건을 확인 | 추정 endpoint 없음, 인증·호출 제한 기록 |
| 1. fixture | source-specific 정상/오류 응답과 parser 검증 | fixture와 계약 테스트 통과 |
| 2. offline 통합 | 저장, 검증, 조회, 중단·재개 E2E | 출처·hash·단위·주기·missing/zero invariant 유지 |
| 3. 짧은 live canary | 승인된 최소 요청, 보통 15–30분 | 예상 응답·호출량·오류율·키 마스킹 확인 |
| 4. 2시간 run | 중단·재시도·부분 실패·재개 확인 | provider budget 내에서 run 종료 |
| 5. 6시간 이상 soak | 장기 저장 증가·메모리·rate behavior·복구 확인 | 안전 중단/재시작 후 결과 재현 |

첫 live 시험은 provider당 동시 요청 1개를 기본으로 하며, 공식 제한과 안정성이 확인된 경우에만 운영자가 상향합니다. 같은 API provider를 쓰는 여러 기관 profile은 요청 budget을 공유합니다. 401/403, 429, 응답 schema 변화, 반복 timeout, 저장공간 상한, 값의 급격한 검증 실패가 생기면 그 source만 중단합니다. 다른 source의 offline 작업은 이어갈 수 있습니다. 이 시간은 MacroAtlas의 운영 단계이며 기관의 공식 rate limit을 뜻하지 않습니다.

## 언어와 번역

1. 영어 API, 영문 카탈로그, 영문 코드 목록과 영문 정의가 있으면 먼저 사용합니다.
2. 영문 자료가 없을 때만 필요한 일본어 또는 중국어 원문으로 내려갑니다.
3. 수집 데이터와 원문 라벨은 바꾸지 않고 보존합니다. 의미 설명이 필요하면 원문 → 영어 중간 표현 → 한국어 설명 순서로 진행합니다.
4. 원문, 사용 언어, 번역문, 번역 근거와 확인 필요 여부를 분리합니다. 공식 번역으로 가장하지 않습니다.
5. 수치, 단위 기호, 코드, 날짜, 식별자는 번역하지 않습니다. 의미가 바뀔 수 있으면 사람 검토로 돌립니다.

## 역할과 승인

| 역할 | 책임 |
|---|---|
| 사용자/연구자 | 필요한 통계·범위·우선순위를 설명하고, 정의가 애매한 결과를 확인 |
| 운용자 | 로컬 인증 값, 네트워크 허용, 일정과 쿼터를 관리하고 위험 시 중단 |
| 개발자 | 공통 엔진·source adapter·fixture·회귀 검사 및 문서 유지 |
| 에이전트 | 자연어 지시를 정리하고, 근거와 불확실성을 모아, 제한된 변경/결과를 설명 |
| 사람 검토자 | 코드 diff, 공통 규칙 승격, 외부 live 시험과 통합을 검토 |

에이전트 역할은 목표 업무 모델입니다. 현재 제품 UI, 예약 자동 개선, 실제 멀티에이전트 운영이 이미 존재한다고 말하지 않습니다. 실제 수집 키는 소스·테스트·대화·로그에 출력하지 않습니다.

## 향후 4주 권장 운영안

| 기간 | Track M | Track C | 확인할 산출물 |
|---|---|---|---|
| 1주차 | 첫 주간 오류/피드백 triage와 미해결 목록 정리 | 다음 기관 후보와 필요한 dataset 범위 선택 | 단일 우선순위 큐, 저장소 현황 |
| 2주차 | 첫 격주 메모리/성능 paired 기준선 | 선택 기관 문서·인증·mock fixture·adapter 설계 | 측정 재현 방법, source contract |
| 3주차 | 발견된 공통 병목이 있을 때만 수정/회귀 | source offline E2E와 저장/복구 게이트 | 코드 diff와 기관별 결과 |
| 4주차 | 다음 주간 피드백 주기, 지표 검토 | readiness를 통과한 기관만 canary 검토 | 통과·보류 근거와 다음 4주 큐 |

이 일정은 학습 주기이지 모든 기관을 4주 안에 live로 연결한다는 약속이 아닙니다. 게이트가 실패하면 해당 source는 멈추고 원인을 보완합니다. 다른 독립 업무는 계획 범위에서 계속할 수 있습니다.

## 보존할 기록

운영 기준 문서는 현재 방향을 설명하고, 이미 완료된 사실은 변경하지 않는 보고서에 보존합니다. 회차별 보고서, DECISION_LOG.md, OPTIMIZATION_LOG.md, 기준선·비교·회귀 보고서와 reports/ 원시 측정은 이력 증거로 유지합니다. 이번 설명 문서와 과거 변경 로그가 충돌하면 제품 범위는 PROJECT_PLAN, 주기/실행은 이 문서, 측정 결과는 해당 보고서를 따릅니다.
