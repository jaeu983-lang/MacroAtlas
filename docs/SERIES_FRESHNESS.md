# Frequency-aware series freshness

This document describes the implemented freshness gate for source observation
periods. It checks how recent the newest observation is for its own cadence; it
does not treat a recent download or metadata refresh as evidence of recent data.
The integrated product scope and remaining work are tracked in [`PROJECT_PLAN.md`](../PROJECT_PLAN.md).

## Current policy

The versioned default policy is `frequency_max_age_v2`. It measures calendar
days from the end of the newest observed period to the UTC evaluation date.
The default maximum ages are:

| Frequency | Maximum age |
|---|---:|
| Daily | 7 days |
| Weekly | 21 days |
| Monthly | 120 days |
| Quarterly | 240 days |
| Semiannual | 183 days |
| Annual | 730 days |

These are configurable operational defaults, not release-calendar guarantees
or universal rules for every series. A caller can inject a `FreshnessPolicy`
with revised frequency limits or exact series overrides. Overrides accept
`series_id:<source-series-id>` or a canonical `series_key:` generated by
`series_key_override_key`; a series ID override takes precedence over a series
key override, which takes precedence over the frequency default. An exact
override is applied only when it is linked to a `FreshnessEvidence` record with
a supported evidence type, credential-free HTTPS reference, captured document
SHA256/time, citation, and explicit `approved` review metadata. Missing,
pending, or rejected evidence makes that exact-series result
`FRESHNESS_UNVERIFIED`; the evaluator does not silently fall back to a broader
frequency tolerance. The policy fingerprint includes the override and evidence
metadata.

The evidence model records an operator's reference and review attestation; it
does not download the URL, verify that the SHA256 corresponds to that URL, or
authenticate the reviewer. No source-specific approved release-calendar
evidence is seeded by this implementation. Frequency defaults remain the only
currently active built-in policy and are labeled `frequency_fallback`.

## Decision and data handling

The evaluator finds the newest period with an actual value and converts it to
its calendar period end. A row whose value is null or missing remains preserved
but does not make that period an available observation. If every value is
missing, freshness is `FRESHNESS_UNVERIFIED`. For example, a monthly `2026-06`
observation is evaluated as of June 30, not June 1. A result is `FRESH` when its age is within the
configured maximum, `STALE` when it exceeds that maximum, and
`FRESHNESS_UNVERIFIED` when the frequency, tolerance, or period evidence is
missing or invalid, or the observation period is in the future. When source
frequency metadata is unknown, a recognized explicit period format can support
the freshness calculation; this does not fill in or alter the source's
normalized frequency metadata.

`STALE` and `FRESHNESS_UNVERIFIED` values are withheld from normalized result
payloads and CSV export. The original source response and its manifest remain
preserved for review. The quality record includes status, cadence and its
basis, latest period and period end, age, allowed age, exact override key,
policy evidence status/reference, evaluation timestamp, policy ID/fingerprint,
and a reason. CSV export
re-evaluates freshness at export time and requires a matching successful
quality record, so a series that became stale after collection is blocked.

No values are interpolated, forward-filled, or otherwise changed by this gate.
Null and missing source rows are still retained in the raw and parsed series;
only the freshness anchor excludes them. The gate assesses the newest available
period only; it does not prove that all expected periods are present, detect
statistical outliers, or establish cross-source equivalence.

## Implemented paths and limits

The shared evaluator is connected to the current World Bank, BLS, Census, BOJ,
and explicitly mapped local tabular-file paths. A file mapping must declare its
period/value columns and cadence; the runtime does not infer these fields. A
stale or unverified mapped file is preserved for review and does not complete
successfully. Successful API series and mapped-file series are saved under
`data/processed/typed_series/` as JSON artifacts. Their contract records link
the raw response and source manifest, and a separate manifest records hashes of
the typed artifact and both source files. Artifact loading rechecks all of those
hashes and stored freshness states. `export-xlsx` verifies the artifact and its raw/manifest
references, then re-evaluates freshness at export time using the current policy and clock.
It emits a source-value workbook and hash-linked provenance sidecar without overwriting.
This connection is fixture-verified and is not evidence that each provider's release calendar
has been measured.
These are local deterministic tests and code-path
coverage; they do not establish live API freshness behavior or validate each
source's publication calendar. Unmapped generic tabular data has no normalized
series-frequency contract and is not covered by this gate. Bloomberg is not an
integrated connector in this repository.

`acs/acs1`, variable `B01001_001E`, California (`state:06`). Those margins are

returned the scheduled September 2026 period after the official calendar date
of October 14 at 08:30 EDT. This is one post-release availability sample at
T+14 days 12 hours; it does not establish first availability, a repeated
latency bound, or the proposed 60-day threshold. The BLS 60-day proposal
remains pending and the Census 400-day candidate remains rejected; neither
